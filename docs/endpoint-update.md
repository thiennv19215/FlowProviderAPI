# Endpoint update: normalized statuses and Provider-owned media

This document describes the public API changes that downstream applications must adopt.

## Breaking status change

Generation and media endpoints now use one public status vocabulary:

| Status | Meaning | Terminal |
|---|---|---|
| `queued` | The generation is waiting for a worker or provider capacity. | No |
| `running` | The generation is being processed or polled. | No |
| `done` | The generation or media operation completed successfully. | Yes |
| `failed` | The operation failed. Inspect `error`. | Yes |
| `canceled` | The generation was canceled. | Yes |

Replace old comparisons as follows:

| Old value | New value |
|---|---|
| Generation `succeeded` | `done` |
| Media `ready` | `done` |

The old public values are no longer returned or accepted by status filters.

## Submit a generation

`POST /v1/generations`

Headers:

```http
Authorization: Bearer <FLOW_PROVIDER_API_KEY>
Content-Type: application/json
Idempotency-Key: <stable-key-for-this-logical-submission>
```

Example request:

```json
{
  "kind": "image",
  "prompt": "A premium product photo",
  "media_ids": ["123456789012345"],
  "options": {
    "model": "NANO_BANANA_2",
    "aspect_ratio": "9:16",
    "output_count": 1
  }
}
```

Accepted response (`202`):

```json
{
  "task_id": "job_abc123",
  "status": "queued",
  "outputs": [],
  "error": null
}
```

Use the same `Idempotency-Key` when retrying the same logical submission. Reusing the key with a different normalized request returns `409 IDEMPOTENCY_KEY_CONFLICT`.

## Poll generation status

`GET /v1/status/{task_id}`

Poll while status is `queued` or `running`. Stop when it becomes `done`, `failed`, or `canceled`.

Successful response:

```json
{
  "task_id": "job_abc123",
  "status": "done",
  "outputs": [
    {
      "media_id": "234567890123456",
      "type": "image",
      "url": "https://provider.example.com/media/234567890123456",
      "thumbnail_url": null
    }
  ],
  "error": null
}
```

Failed generation response (`GET` still returns HTTP `200` because the lookup succeeded):

```json
{
  "task_id": "job_abc123",
  "status": "failed",
  "outputs": [],
  "error": {
    "status_code": 429,
    "code": "RESOURCE_EXHAUSTED",
    "message": "Generation quota is exhausted.",
    "details": [],
    "request_id": "req_abc123",
    "retryable": true
  }
}
```

List and filter tasks with:

```http
GET /v1/status?status=done&limit=20
```

`status=succeeded` is no longer valid. Use `status=done`.

## Upload reference media

`POST /v1/media`

Send multipart form data with a required `file` and an optional `type` (`image` or `video`).

Successful response (`201`):

```json
{
  "media_id": "123456789012345",
  "object": "media",
  "type": "image",
  "status": "done",
  "mime_type": "image/png",
  "size_bytes": 182731,
  "width": null,
  "height": null,
  "duration": null,
  "url": "https://provider.example.com/media/123456789012345",
  "created_at": "2026-08-13T00:00:00Z"
}
```

`media_id` is always a 15-digit JSON string. Do not parse or store it as a JavaScript number.

## Media delivery and ownership

Generated images and videos are copied into Provider-owned storage (R2 in production). Output URLs point to the authenticated Provider delivery endpoint:

```http
GET /media/{media_id}
Authorization: Bearer <FLOW_PROVIDER_API_KEY>
```

The downstream backend must forward its Provider API key when downloading the URL. Do not place this API key in browser code. If a browser needs the media, the downstream backend should proxy it or copy it into application-owned storage and return an application-authorized URL.

The public `media_id` is generated by FlowProviderAPI. Google Flow media IDs remain internal.

## Downstream migration checklist

1. Change generation success checks from `status === "succeeded"` to `status === "done"`.
2. Change media success checks from `status === "ready"` to `status === "done"`.
3. Treat only `queued` and `running` as non-terminal generation states.
4. Update status filters from `status=succeeded` to `status=done`.
5. Store every `media_id` as a string.
6. Persist `task_id` immediately after a `202` response.
7. Retry ambiguous generation submissions with the same `Idempotency-Key`.
8. Download `/media/{media_id}` server-side with the Provider Bearer key.
9. Inspect the nested `error` whenever status is `failed`, even though status lookup returns HTTP `200`.

Suggested TypeScript types:

```ts
type ProviderStatus = "queued" | "running" | "done" | "failed" | "canceled";
type MediaId = string;

type ProviderOutput = {
  media_id: MediaId;
  type: "image" | "video";
  url: string | null;
  thumbnail_url?: string | null;
};

type GenerationStatus = {
  task_id: string;
  status: ProviderStatus;
  outputs: ProviderOutput[];
  error: {
    status_code: number;
    code: string;
    message: string;
    details: Array<{ field?: string | null; code: string; message: string }>;
    request_id: string | null;
    retryable: boolean;
  } | null;
};
```
